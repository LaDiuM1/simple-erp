# 데모 UX 전수 점검 체크리스트

## 점검 기준

- 기준 화면: 데스크톱 1600 × 900, 데모 매니저 계정
- 점검 방식: 실제 로컬 데모의 각 경로를 로딩 완료 후 캡처하고, 정보 위계·가독성·업무 맥락·공간 사용·행동 가능성을 확인한다.
- 데이터 원칙: 모두 허구여야 하지만 화면에 `샘플`, `가상`, `합성`, `SAMPLE`, `SYNTH`를 반복 노출해 업무 맥락을 훼손하지 않는다. 안전성은 고지, 예약 도메인과 무효 연락처, 내부 검증 표식으로 보장한다.
- 코드 원칙: 화면별 임시 CSS가 아니라 공통 컴포넌트 옵션과 명시적인 도메인 구성으로 해결한다.

## 전역

- [x] 화면과 안내의 명칭을 `데모`로 통일한다.
- [x] 합성 데이터·실제 개인정보 입력 금지·초기화 시각 고지는 유지한다.
- [x] 데모 계정 사용자명·부서명과 기준정보를 실제 ERP처럼 읽히는 허구 데이터로 바꾼다.
- [x] 넓은 화면에서 고정 폭 열이 함께 축소되어 식별자·날짜·금액이 불필요하게 잘리지 않게 한다.
- [x] 좁은 화면에서는 중요 열 최소 폭과 가로 스크롤을 보존하고, 말줄임 값에는 전체 내용을 확인할 방법을 둔다.
- [x] 검색·초기화·주요 행동의 정렬과 간격이 목록마다 일관적인지 확인한다.

## 화면별 발견 사항

- [x] 대시보드: 환영 배너, 단순 KPI, 계약·AS 표, 최근 목록이 같은 우선순위로 이어지는 카드 모음을 업무 현황 중심의 명확한 위계로 전면 재구성한다.
- [x] 부서·직책: `가상 주식회사`, `합성 ...`, `합성 직책` 같은 검증용 표현을 실제 조직처럼 읽히는 명칭과 설명으로 바꾼다.
- [x] 직원: `가상직원NN`, `seed.userNN`, 반복 무효 전화번호와 긴 이메일이 화면을 테스트 fixture처럼 보이게 하는 문제를 해소한다.
- [x] 고객사·영업 명부·영업 고객: 반복 회사명·담당자명·주소·활동 경로를 서로 연결된 실제 영업 업무 이야기처럼 구성한다.
- [x] 공급사·제품: `SAMPLE VENDOR`, `SAMPLE-*` 모델명을 허구 제조사와 일관된 제품군·모델 코드로 바꾼다.
- [x] 계약: 계약번호·고객사·설비명·담당자·날짜·금액의 불필요한 말줄임을 줄이고 금액 비교가 쉽도록 정렬한다.
- [x] 설비: `SYNTH-*`, `가상시 샘플산단`을 제거하고 모델·시리얼·설치 주소·보증 기간을 한눈에 비교할 수 있게 한다.
- [x] AS: 넓은 공간에서도 접수번호·접수일·담당자·설비가 잘리는 열 배분을 바로잡는다.
- [x] 전자결재·경비: `합성 LEAVE/EXPENSE/GENERAL 문서` 같은 fixture 제목을 실제 기안 제목과 경비 내역으로 바꾼다.
- [x] 근태: 오늘 출퇴근, 월별 기록, 위치 모의 고지의 정보 위계와 빈 상태를 확인한다.
- [x] 게시판: `합성 NOTICE/FREE/MEETING 게시글`을 실제 사내 공지·회의록·업무 공유 제목과 본문으로 바꾼다.
- [x] 드라이브: 페이지 제목 아래 `드라이브`가 한 번 더 표시되는 빈 필터 영역을 공통 컴포넌트 옵션으로 숨기고, 하위 경로 탐색 정보는 유지한다.
- [x] 권한·코드 채번: 관리 화면의 상태·설명·행동 위계와 빈 공간을 확인한다.

## 검색·선택 모달 정보 경계

- [x] 직원 선택은 이름·부서·직책·로그인 ID만 보여주고, 과거 직원 조회에서만 상태를 추가한다. 권한·이메일·전화·입사일·생년월일은 노출하지 않는다.
- [x] 고객사 선택은 고객사명·코드·대표자·전화·분류·상태처럼 식별과 거래 가능 여부 판단에 필요한 정보만 유지한다.
- [x] 고객사가 고정된 영업 명부 선택에서는 현재 소속·컨택 경로·최초 미팅일을 반복하지 않고, 담당자를 구분할 이름·직책·부서·휴대폰·이메일만 보여준다.
- [x] 고객사가 고정된 AS 설비 선택에서는 고객사 열을 반복하지 않고 모델·시리얼·설치 주소·설치일·무상 AS 기간을 보여준다.
- [x] 부서·직책·권한 선택은 관리 목록을 재사용하지 않고 각각 이름을 대표 정보로 둔 목적별 컬럼 구성을 사용한다.
- [x] 제품 모델과 컨택 경로 선택은 기존 구성이 선택 목적에 맞는지 확인하고 불필요한 공통 추상화를 추가하지 않는다.
- [x] 데스크톱과 모바일에서 필터·대표 정보·행 선택·확인 후 폼 반영이 정상인지 실제 브라우저로 검증한다.
- [x] 단일선택 라디오는 후보명과 접근 가능한 이름을 공유하고 같은 그룹으로 묶어 키보드·보조기술에서도 대상을 구분할 수 있게 한다.

## 업로드 기능 검증

- [x] `READY`에서는 업로드를 허용하고 reset이 시작되면 즉시 잠가 DB와 파일 generation이 함께 복원될 때까지 다시 열지 않는다.
- [x] READY에서 고객사 Excel과 영업 명부 Excel의 업로드 버튼이 노출되고, 내려받은 템플릿으로 만든 실제 XLSX의 성공·오류 응답이 화면 계약과 일치하는지 확인한다.
- [x] READY에서 게시판·전자결재·경비 첨부와 Drive 업로드가 기존 권한·다운로드 UX를 보존하는지 확인한다.
- [x] Caddy·Spring request 32MB와 Spring·UI 파일당 30MiB 상한이 충돌하지 않는지 정확히 30MiB 성공·1byte 초과 413으로 확인한다.
- [x] reset 진입 즉시 업로드를 포함한 쓰기가 잠기고, startup 검증과 VERIFYING이 끝나 READY가 되기 전에는 다시 열리지 않는지 순서 계약·백엔드 테스트·E2E로 확인한다.
- [x] 고객사 Excel·영업 명부 Excel·공통 첨부·Drive의 업로드→조회·다운로드→backend 재시작→reset→DB·파일 부재를 실제 이미지 acceptance로 확인한다.
- [x] 앱에서 연결을 삭제한 파일의 물리 삭제를 reset이 소유하고, reset 성공 시 직전 generation과 방문자 파일 bytes가 같은 주기에 제거되는지 확인한다.

## 재검증

- [x] 수정된 별도 실행 환경에서 동일 경로를 다시 캡처한다.
- [x] 관리자형·직원형 계정의 메뉴와 권한 차이가 유지되는지 확인한다.
- [x] 목록 검색·정렬·페이지 이동, 상세 진입, 대표 생성 폼 열기가 정상인지 확인한다.
- [x] 대시보드의 카드·링크·데이터 범위가 기존 API와 권한 계약을 보존하는지 확인한다.
- [x] seed 재현성·manifest·MariaDB 불변식과 frontend lint·typecheck·test·build를 통과한다.
- [x] 독립 기능 리뷰와 독립 코드 구조 리뷰에서 P1/P2가 남지 않는다.

## 검증 증거

- 격리 환경: 원본 데모 `127.0.0.1:18080`과 분리한 `127.0.0.1:28080`에서 DB·backend·web 컨테이너를 별도 실행했다.
- 시각 감사: 주요 목록·대시보드·로그인·직원형 계정·대표 생성 폼·드라이브 하위 경로를 포함한 기존 최종 캡처 34개와 검색 모달 캡처 7개를 로딩 완료 후 확인했다. 기본 해상도는 1600 × 900이며, AS 목록은 2048 × 1024, 대시보드·AS 목록과 직원·고객사·제품·설비 선택 모달의 모바일 경계는 390 × 844로 추가 확인했다.
- 캡처 보관: 커밋에는 포함하지 않는 로컬 리뷰 아티팩트 `simple-erp-demo-ux-audit/{before,after-final,modal-search-final}`에 전후 증거를 분리했다.
- 시드·제어 계약: 고정 Linux 환경의 control-plane 테스트 41개와 정적 데모 계약 테스트 23개, 159,900개 reset 시각 속성 테스트, byte-for-byte 재현성 검사를 통과했다. MariaDB 11.8.6 fresh import 후 `verify-seed.sql` 위반은 0건이었다.
- 백엔드: 전체 68개 suite·758개 테스트에서 실패·오류 0건을 확인했다. Windows에서 POSIX 권한 전용 fixture 4개는 명시적으로 건너뛰고, 공유 GID·2775 연월 디렉터리와 capability 없는 reset 삭제 계약은 Linux 컨테이너 및 실제 이미지 acceptance로 별도 확인했다. 파일 메타데이터 정규화, 임시 파일 원자 승격, 트랜잭션 rollback 정리, startup 쓰기 gate와 READY/VERIFYING 파일 정합성 회귀를 포함한다.
- 프런트엔드: ESLint, TypeScript typecheck, Vitest 40파일·120테스트, production build를 통과했다. Playwright는 격리된 UX 경계 1건과 `127.0.0.1:28080`의 실제 backend·DB 연결 종단 흐름 1건을 Chromium에서 각각 통과했다.
- 사용자 흐름: 고객사 검색·초기화·정렬·페이지 이동·상세 진입, 대표 생성 폼, 관리자형/직원형 권한 경계와 대시보드 데이터 범위를 확인했다. 직원·고객사·영업 명부·설비·제품·부서·직책·권한 선택 모달은 목적별 헤더와 필터를 대조하고 실제 행 선택 후 폼 반영까지 검증했다.
- 독립 리뷰: 시드 현실성·기능 회귀·접근성·반응형·공통 컴포넌트 구조·테스트 유지보수성을 재검토한 뒤 P1/P2/P3 잔여 항목 0건으로 종료했다.
- 업로드 복구 검증: 격리된 실제 이미지 환경에서 고객사 Excel·영업 명부 Excel·30MiB 공통 첨부·Drive 업로드를 실행했고, 조회·다운로드와 backend 재시작 뒤 정합성을 확인했다. 1byte 초과 첨부는 413으로 거부됐으며, 후속 reset에서 생성 행·파일 API와 이전 generation 디렉터리·업로드 bytes가 모두 사라졌다.
